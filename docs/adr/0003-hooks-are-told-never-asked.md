# Hooks are told, never asked

> The config keys and environment variables below were spelled `git-switch.*` and `GIT_SWITCH_*` when this was written. They are now `perch.*` and `PERCH_*`, with no fallback — see [ADR 0006](./0006-named-for-the-motion-not-the-mode.md). The decision is unchanged; only the spelling is.

> `--hook-env KEY=VALUE` lets whoever runs `perch` add variables beside the payload. The payload wins a clashing key, so the schema a hook can rely on is still `perch`'s alone, and the hook is still only told.

Worktrees created by `git-switch wt` have a life outside git — an editor or session manager wants to open them, and to forget them again when they go. Git covers half of that already: `git worktree add` fires `post-checkout`, distinguishable from an ordinary checkout by the null SHA it passes as the previous ref. Git fires *nothing* on `git worktree remove` — confirmed against githooks(5)'s closed list, the single hook call site in `builtin/worktree.c`, and empirically on git 2.55. Rather than an integration living half in a git hook parsing SHAs out of `$1` and half in `git-switch`, both moments are `git-switch`'s: two shell commands read from git config, `git-switch.hook.created` and `git-switch.hook.removed`, run for their effect and never consulted. A hook is told what happened; it is never asked.

The alternative to building anything was the `post-checkout` route plus living without teardown, and it is a real option — it is why this decision needed recording at all. See [the research snapshot](../research/post-switch-hooks.md) for what git, jj, gh, cargo and direnv each do, pinned to the versions it was checked against.

## Consequences

- **A hook cannot influence what `git-switch` does.** It cannot veto a removal, and above all it cannot grant a [License](./0001-warned-means-forceable.md): every destructive step is licensed by a marker the user was shown or an explicit `--force`, and admitting a second source of permission — one that answers on the user's behalf without showing them anything — would undo that rule rather than extend it. A hook that exits non-zero is reported and ignored, matching how every other non-git failure in `wt` behaves. The worktree is real whether or not anything else heard about it, and blocking a `cd` on an editor integration is the tail wagging the dog.
- **`git-switch` drives; nothing drives `git-switch`.** The inverse — an editor shelling out to `git-switch wt` when it creates a workspace — would require that editor to know the worktree path convention, the base-branch rule and the shell wrapper. It remains available as an addition, but two write paths into the same state is a consistency problem this does not need. Hooks are also generic: no third-party tool is named anywhere in the codebase, which is what keeps `CONTEXT.md` free of anyone else's vocabulary and leaves us with no schema to track but our own.
- **Config lives in git config, so the trust question mostly dissolves.** `git-switch.keep` already established the namespace, `git config` layering gives a global hook that any single repo can override, and no config-file parser is added. Decisively, `.git/config` is not transferred by `git clone`, so a repo cannot ship a hook to whoever clones it. Git-style executable scripts in a tracked directory would recreate exactly the problem git needed a trust model to answer, and jj states the rule outright — *"For security reasons, they are not located inside the repo"*.
- **Hook stdout is captured and re-emitted on stderr.** The handoff writes the destination path to stdout for the shell wrapper to `cd` into, so an inherited stdout means a chatty hook silently sends the user somewhere absurd. Capturing is the only arrangement that cannot corrupt it. Hook stderr passes through untouched.
- **Creation fires before the stale-branch prompt, not after.** That prompt is interactive and an interrupt propagates as an error, so a hook placed after it would never run when the user hits Ctrl-C — leaving a worktree on disk that nothing was told about. Firing the moment the worktree exists makes the hook a consequence of creation and of nothing else.
- **Removal fires after a successful removal, once per worktree.** A hook that fired on an aborted removal would be worse than one that fires late, and the multi-select path removes several worktrees in a loop, where a single batched run would claim all of them the moment one of them failed. The cost is that the hook receives a path already gone from disk — fine for *forget this*, useless for anything wanting to read the directory. Recovering state about a removed worktree is therefore the hook's problem, and whether it is even possible depends on the tool being called: git's own worktree registry cannot answer it, because the record is what was just destroyed.
- **Hooks are indifferent to whether there is a terminal.** A hook is not a prompt, and gating it on a TTY would let a scripted `wt rm --force` desynchronise the very state this exists to keep in step. `GIT_SWITCH_NO_HOOKS=1` is the escape hatch, which is also what keeps the test suite hermetic.
- **Deliberately not built:** hooks on in-place branch switching or on entering an existing worktree — neither creates or destroys anything for a hook to mirror, and the latter would fire on every navigation; hook chaining, since `cmd1 && cmd2` says it more plainly than a list syntax and git's own last-value-wins semantics should not be departed from inside git's own config file; timeouts and detached execution, since a fire-and-forget hook that dies has nowhere to report and would contradict the advisory contract by being silent rather than warning.
